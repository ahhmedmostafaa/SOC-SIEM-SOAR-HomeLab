# Detection 02 — Kerberoasting Detected

| | |
|---|---|
| **MITRE ATT&CK** | T1558.003 — Kerberoasting |
| **Data Source** | Windows Security Log, Event ID 4769 (Kerberos Service Ticket Request) |
| **Severity Logic** | ≥10 unique SPNs → Critical, ≥5 → High, else Medium |

## Attack Simulated

From Kali, Impacket's `GetUserSPNs.py` was used to enumerate and request Kerberos service tickets for every account in the domain with a registered SPN — the standard first step of a real Kerberoasting attack, immediately preceding offline password cracking:

```bash
GetUserSPNs.py soclab.internal/karim.nabil:'Pass@word!' -dc-ip 192.168.20.10 -request
```

This mirrors exactly how tools like Rubeus or `Invoke-Kerberoast` operate: authenticate as any valid domain user, then request TGS tickets for every SPN-bearing account (such as `svc.backup`, deliberately created with an SPN for this purpose — see [`infrastructure-setup/02`](../infrastructure-setup/02-active-directory.md)) in order to extract them for offline cracking.

## Detection Logic

```spl
index=* EventCode=4769 Ticket_Options=0x40810010 Service_Name!="krbtgt" Service_Name!="*$"
| eval Account_Name=replace(Account_Name, "@.*$", "")
| eval Account_Name=replace(Account_Name, "^.*\\\\", "")
| eval Client_Address=replace(Client_Address, "^::ffff:", "")
| stats dc(Service_Name) as unique_spns, values(Service_Name) as targeted_spns, count as total_requests, min(_time) as first_seen, max(_time) as last_seen by Account_Name, Client_Address
| where unique_spns >= 3
| eval severity=case(unique_spns>=10, "Critical", unique_spns>=5, "High", true(), "Medium")
| eval alert_name="Kerberoasting Detected (4769)"
| eval mitre_technique="T1558.003 - Kerberoasting"
| convert ctime(first_seen) ctime(last_seen)
| eval targeted_spns_str=mvjoin(targeted_spns, ", ")
| eval recommended_actions="Multiple Service Principal Names (SPNs) requested by " . Account_Name . " - possible Kerberoasting attempt.;;Check whether " . Account_Name . " normally requests service tickets for these SPNs.;;Review the service accounts targeted (" . targeted_spns_str . ") for weak or crackable passwords.;;If suspicious, reset the password of " . Account_Name . " and the targeted service accounts.;;Enable AES encryption for service accounts to prevent offline cracking."
| eval alert_type="kerberoasting", source_ip=Client_Address, target_identity=Account_Name, host="N/A (domain-wide event)"
| table alert_name, alert_type, mitre_technique, severity, host, target_identity, source_ip, unique_spns, total_requests, targeted_spns_str, first_seen, last_seen, recommended_actions
```

### Why it's built this way

- **`Ticket_Options=0x40810010`** is the specific combination of Kerberos ticket flags (`Forwardable`, `Renewable`, `Canonicalize`, `Renewable-ok`) that .NET-based ticket-request libraries — the ones used internally by common Kerberoasting tools — send by default. This acts as a fingerprint that separates automated bulk requests from the Kerberos traffic generated by normal domain operations.
- **`Service_Name!="krbtgt"` and `!="*$"`** exclude the ticket-granting-ticket service itself and machine accounts, both of which generate enormous volumes of *legitimate* 4769 traffic (domain controllers and member machines constantly request tickets for each other) that would otherwise completely drown the signal.
- **`dc(Service_Name) >= 3`** (distinct SPN count) is the actual trigger, not raw event volume — a single service being requested many times is normal; the same account requesting tickets for *three or more different* services in a short window is not.
- **`::ffff:` prefix stripping** on `Client_Address` normalizes IPv4-mapped IPv6 addresses (a quirk of how Windows logs Kerberos client IPs) so the IP correlates cleanly with other detections and enrichment lookups downstream.

## False-Positive Awareness

Early testing surfaced background Kerberos traffic from machine accounts (`LAB-DC1$@SOCLAB.INTERNAL`) that initially inflated event counts in broader queries used for incident-timeline reconstruction — this confirmed the importance of the `Service_Name!="*$"` exclusion specifically in the detection logic, even though a raw unfiltered timeline query still needs manual review to separate signal from this kind of normal domain chatter.

## Alert Configuration

| Setting | Value |
|---|---|
| Schedule | Cron `*/5 * * * *` (every 5 minutes) |
| Search window | Last 5 minutes |
| Expires | 24 hours |
| Trigger condition | Number of results > 0 |
| Trigger | **Once** per run |
| Throttle | ✅ Enabled |
| **Suppress results containing field value** | `target_identity` |
| Suppress triggering for | 30 minutes |
| Trigger Actions | Add to Triggered Alerts (**Severity: High**) + **Webhook** → Shuffle `SOC-Master-Playbook` |

A single scheduled alert runs this entire query, with the `severity` field computed dynamically inside the SPL itself (`case(unique_spns>=10, "Critical", ...)`) rather than relying on Splunk's static per-alert severity dropdown. This was a deliberate design choice: Splunk's built-in "Triggered Alert" severity is normally a fixed value set once when the alert is created, which would display the same severity label every time the alert fires regardless of how many SPNs were actually targeted in that run. Consolidating the threshold logic into the search itself — and carrying the computed `severity` field all the way through to the SOAR payload — keeps the detection as one maintainable alert while still giving the downstream Shuffle playbook an accurate, incident-specific severity every time, instead of maintaining three near-duplicate alert definitions that would all need updating in lockstep if the thresholds ever changed.

Suppressing on `target_identity` (the account being Kerberoasted, not the source) means repeated TGS requests against the same account within a 30-minute window are treated as one ongoing incident rather than re-notifying every 5 minutes.
